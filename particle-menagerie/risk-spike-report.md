# Risk-Spike Report — Particle Menagerie v3 (three.js rebuild)

Adversarial review of `CLAUDE.md`, `particle-menagerie-prd.md`, `threejs-approach.md`, `threejs-critical-breakdown.md`, and the v2 prototype (`particle-menagerie.html`). Scope: what the plan gets wrong or misses — not what the 10-item register already covers. Findings marked **[verified]** survived adversarial verification (severity shown is the refined rating); findings marked **[unverified]** are lower-confidence and were not adversarially re-checked.

---

## 1. Executive summary — the five biggest loopholes

- **Every automated performance gate is invalid where the tests run.** This environment has no GPU (`/dev/dri` absent); headless Chromium renders WebGL via SwiftShader at a measured **2.9 fps** for the planned workload (25k additive 24px sprites). CLAUDE.md's "count rAF ticks, keep doing this" convention silently stopped being meaningful the moment the project switched from Canvas2D to WebGL. Phase 0/1/3 FPS exits are unmeasurable as written, and Risk 5's fill-rate mitigation can never be validated in the harness. *(verified, high)*
- **The trails accumulation target — the plumbing Risk 3 calls "standard, ~50 lines" — has two unspecified decisions that each produce a guaranteed artifact.** Default 8-bit precision makes multiplicative fade quantize and stall: a permanent gray ghost of every path ever swum. Half-float fixes that but lets near-stationary flora accumulate to `input/(1−fade)` — ACES then renders every rooted anemone as a desaturated white blob. Neither precision nor energy normalization appears in any doc. *(verified, high)*
- **The performance budget was never re-run for the pipeline Phase 0 actually mandates.** `threejs-approach.md` §7 ("fine at 1080p", "60fps with 16 creatures on integrated graphics") budgets the dead r128 fade-quad-to-screen pipeline; CLAUDE.md replaces it with HDR target + ping-pong trails + tonemap pass (and later bloom), and §3 of the approach doc still specifies the fade quad the other two docs forbid. The 60fps claim is a carry-over, not a budget. The CPU line ("~1–2 ms") also fails its own arithmetic once 3D frames + normals are included. *(verified, high / medium)*
- **The lighting recipe is validated on the one archetype where it's true.** "Every dot's offset direction *is* its surface normal — normals for free" (§2.1) is false for the sheet archetypes (ray ~90% of dots, bloom petals ~72%, fins): the in-plane offset is exactly the wrong normal. Phase 0 gates on the eel (a true ring-tube, the best case), and Phase 1's exit (squint test + 60fps) never checks shading — so the go/no-go can pass while the core trick fails for a large fraction of the menagerie. Frame construction (no reference-vector/RMF spec), curvature exceeding tube radius **at default sway**, and non-arc-length rib spacing are additional register-absent geometry gaps that all land on the Phase 0 showpiece. *(verified, medium ×4)*
- **The docs no longer agree with each other or with the PRD, and nobody owns the reconciliation.** The gate bar ("clearly beats v2") is a much lower bar than the stated goal ("fidelity of the reference video") with no defined comparison procedure; the npm/vite decision kills "single self-contained HTML file", the offline property, Risk 9's zip mitigation, and the "load page" test convention with no replacement delivery story; four PRD requirements (monochrome identity, all-animals, single-file, Canvas2D fallback) are silently dead; and no three.js version is pinned while r152+ color management sits directly under the tonemapping/blowout risk. *(verified medium + unverified cluster)*

## 2. Findings by severity

### HIGH

#### H1. Trails accumulation buffer: precision and energy are unspecified, and both defaults fail **[verified — high]**
**Plan claims:** Risk 3: trails "move to a ping-pong render target — standard, but ~50 lines more"; CLAUDE.md Phase 0: "trails via offscreen accumulation target."
**Failure mechanism:** Two independent traps, neither covered by Risk 3 (which is only about *where* trails accumulate):
1. *Precision.* A hand-rolled `THREE.WebGLRenderTarget` defaults to `UnsignedByteType`. Multiplicative decay `dst *= fade` quantizes: once `v·(1−fade) < 0.5/255` the value rounds back to itself and never decays. At fade=0.95 everything below ~10/255 is stuck forever — and because the buffer holds linear-light values, ACES+sRGB amplifies the residue (linear 0.039 → ~0.21 displayed): a permanent gray veil of every path ever swum against the near-black scene. The 3-minute Phase 3 soak may barely surface it.
2. *Energy.* In half-float, steady-state brightness at a covered pixel is `perFrameInput/(1−fade)` — a 20–100× temporal gain that Risk 2's mitigations (tonemap, per-dot alpha caps) bound per-*frame*, not per-*history*. v2's rooted flora barely moves; at long-trail settings their accumulated values reach the ACES shoulder and render as desaturated white — the color control appears broken exactly where users look. If the slider maps to fade→1.0, accumulation is unbounded (Inf→NaN, permanent until resize).
**Fix:** Mandate `HalfFloatType` for all accumulation targets (half-float blending is safe in WebGL2; full-float needs `EXT_float_blend`). Normalize injected energy by `(1−fade)` so steady-state brightness is slider-invariant. Clamp fade strictly below 1 and clamp accumulation (`min(color, 64.0)`) in the decay pass. Extend the soak test to 10+ minutes with a stationary creature. *(Subsumes the separate low-severity "fp16 never fades to black" finding: even in fp16, add a subtractive epsilon `max(v*k − e, 0)` or dither to guarantee reaching black.)*

#### H2. The performance budget describes a pipeline that no longer exists — "60fps, 16 creatures, integrated graphics" is unsupported **[verified — high]**
**Plan claims:** `threejs-approach.md` §7: GPU fill "fine at 1080p; cap sprite px size"; draw-call row still counts a fade quad; target "60fps with 16 creatures on integrated graphics." CLAUDE.md's re-check instruction covers only Risks 1 and 3 — not the budget.
**Failure mechanism:** §7 was budgeted for r128 draw-straight-to-screen. The mandated Phase 0 pipeline is: additive sprites into a half-float HDR target (2× write bandwidth per blended pixel), ping-pong trail accumulation (extra full-screen read+write), tonemap composite — and Phase 3 adds bloom's blur chain. DPR handling is deferred to Phase 4, so a naive `setPixelRatio(devicePixelRatio)` on a retina iGPU laptop 4×'s every term with no planned lever until the last phase; the full-screen passes alone (~12 GB/s at DPR 2 / 60fps) are a material fraction of an Intel-class iGPU's bandwidth. The only levers that touch post-chain cost — renderScale and a DPR cap — appear in no doc; §7's sole fallback is a dot-density multiplier, which doesn't touch full-screen cost at all. (Partially attenuated: bloom is correctly phased late, and the existing sprite-size cap does govern the dominant sprite-fill term — but nobody has re-run any of the arithmetic.)
**Fix:** Re-issue the budget for the actual pipeline (HDR format, ping-pong, tonemap; with and without bloom) at DPR 1 *and* 2. Pull `renderScale` and `min(devicePixelRatio, 1.5)` into Phase 0. Reconcile `threejs-approach.md` §3/§7 with CLAUDE.md so the docs describe one pipeline.

#### H3. There is no valid performance gate anywhere in the plan: headless WebGL runs on SwiftShader **[verified — high; merges two findings]**
**Plan claims:** CLAUDE.md testing conventions ("count rAF ticks over 2s for FPS... keep doing this"); Phase 0 exit "headless screenshots + FPS"; Phase 1 exit "60fps"; Phase 3 soak "no fps decay"; all against "60fps on integrated graphics."
**Failure mechanism:** Empirically verified on this machine: no GPU device exists (no `/dev/dri`), headless Chromium reports `SwiftShader Device (Subzero)`, and a representative workload (25k additive 24px sprites, dynamic upload, 720p) ran at **2.9 fps**; even 2px sprites reached only 12.4 fps. No browser flag can summon absent hardware. The 24px-vs-2px spread proves the headless number is dominated by software-rasterized fill — precisely the cost (Risk 5: "the real GPU cost") that scales completely differently on real GPUs. The convention was valid for Canvas2D v2 (CPU-rendered everywhere) and silently broke at the WebGL switch. Consequences: every absolute FPS gate through Phase 3 fails vacuously or gets waived; the first honest perf signal arrives on user hardware in Phase 4 — exactly when Risks 4/5 say density/fill problems bite; and the loud 2.9 fps number will pressure gutting glow/density to satisfy a meaningless metric, corrupting the decisive *aesthetic* gate. (The relative Phase 3 soak retains partial leak-detection validity; screenshots render correctly, just slowly.)
**Fix:** Split the gates: (a) headless = correctness, console errors, and **CPU frame-loop budget** asserted via `performance.now()` (the Xeon is roughly representative for JS math); (b) GPU FPS = manual gate on the user's real hardware at Phase 0 and Phase 1 (they judge the eel anyway), with a frame-time HUD baked into dev builds reporting canvas backing size; (c) the test script asserts the `WEBGL_debug_renderer_info` string and loudly labels any SwiftShader FPS as non-evidence.

**Two unverified corollaries that compound H3** *(both stated high, unverified)*:
- *Wall-clock time + per-frame fade makes headless screenshots quantitatively wrong.* Fade decays per rendered frame while motion advances per wall-clock second; at ~3 fps trails render ~20–30× longer than any user will see, so Phase 0 glow/trail calibration and the Phase 3 "no accumulation artifacts" check are judged against an image regime no real machine produces. Fix: frame-rate-independent decay (`alpha = 1 − pow(1−k, dt·60)`) plus a deterministic fixed-step time hook for screenshots.
- *The Phase 4 governor and the screenshot gates are mutually destructive.* A frame-delta-triggered governor instantly floors density under SwiftShader, so every later screenshot shows the maximally degraded scene — or it's disabled for tests and the soak tests a configuration that never ships. Fix: explicit test hook pinning the governor off for aesthetic screenshots; soak asserts on governor telemetry, not fps.

#### H4. gl_PointSize: platform caps, device-pixel semantics, 1px floor, and center-clipping — four real-WebGL behaviors no doc mentions **[unverified — stated high]**
**Plan claims:** approach §4 sizing `aSize × (620 / −mvPosition.z)`; breakdown §2.4 DOF "costs two lines"; Risk 5's "cap sprite pixel size" treated as an app-owned knob.
**Failure mechanism:** (1) The GPU clamps at `ALIASED_POINT_SIZE_RANGE` — ~511 on Safari/Metal-ANGLE, 1024 on D3D-ANGLE, as low as 63 on some GPUs (spec only guarantees 1.0) — so DOF swell silently clamps differently per platform and visibly stops working on 64-cap devices. (2) `gl_PointSize` is in *device* pixels: at DPR 2 every dot renders half the intended CSS size unless multiplied by DPR (which quadruples fill). The 620 constant is tied to the window-height-dependent camera, so dot size drifts with window size. (3) Sizes below 1 clamp to 1px — distant dots render brighter than the attenuation intends and shimmer. (4) Points clip by *center*: a big soft glow sprite vanishes in one frame as its center crosses the screen edge — constant with the wrap-at-edge drift and parallax camera, and the DOM vignette is thinner than a defocused sprite. Bonus: during formation, transient positions at/behind the near plane make `−z ≤ 0` → undefined/huge point size (some drivers flash a screen-sized sprite).
**Fix:** `size = clamp(base·dpr·atten, 1.0, min(appCap·dpr, queriedMax))`; query the range at startup; fade alpha to 0 below ~1.5 device px instead of letting the clamp brighten far dots; clamp view-space z away from the near plane; pick an edge strategy in Phase 0 (guard-band frustum + CSS crop, edge-fade alpha, or stronger vignette — it affects render-target dimensions). If Phase 0 judging demands DOF swell beyond the platform cap, that's a switch to instanced quads and a §3 architecture change — know before the gate.

#### H5. Four PRD requirements are silently dead; no rescoping artifact exists **[unverified — stated high]**
**Plan claims:** PRD §3 "No color — monochrome is the identity"; §6.1 Winged/Quadruped/Biped archetypes, "any animal name"; §7 "single self-contained HTML file... (Canvas2D fallback)".
**Failure mechanism:** (a) "No color" is contradicted by v2's shipped swatches and ~a third of the v3 control catalog. (b) Three of the PRD's 8 archetypes were cut, and the PRD's taxonomy doesn't even match the codebase's 9 (eel/ray/octo/star/bloom/kelp...). (c) npm/vite kills single-file and offline. (d) The Canvas2D fallback appears nowhere in the v3 plan — WebGL-less users now get a black page. Each is a place where the build can be "done per plan" yet fail the requirements doc of record, or where effort is wasted honoring a dead spec.
**Fix:** A ten-minute "superseded requirements" block in CLAUDE.md: monochrome→monochrome-by-default-with-color; scope→ocean+flora, 9 archetypes; delivery→vite build; Canvas2D fallback→dropped (WebGL-required message).

### MEDIUM — verified

#### M1. The HDR-target requirement behind "tonemap in the composite" is stated nowhere, and `renderer.toneMapping` is a silent no-op for the custom shader **[verified — medium; merges 2 findings]**
**Plan claims:** breakdown §2.2 / Risk 2 "tonemap in the (final) composite", rated "easy"; approach §4's shader writes `gl_FragColor` directly with no render target mentioned.
**Failure mechanism:** In three.js, tonemapping is per-material and pre-blend — and *not applied at all* to a custom `ShaderMaterial` unless the chunk is included manually. Tonemapping only bounds the additive *sum* if the scene renders with `toneMapped=false` into a **linear half-float target** with ACES+sRGB in one final pass. The plan does say "in the composite," and modern EffectComposer+OutputPass defaults do exactly the right thing — but no doc says "floating-point target," and the *hand-rolled trails ping-pong pair* (not a stock composer pass) defaults to `UnsignedByteType`: a doc-compliant implementer can silently clip the additive sum pre-tonemap and reproduce the exact blowout Risk 2 calls a top killer, then wrongly conclude "tonemapping doesn't fix it" — at the project's single go/no-go moment.
**Fix:** One load-bearing sentence in the Phase 0 spec: *all* accumulation targets are `HalfFloatType` linear; exactly one tonemap and one sRGB encode, both in the final pass; `renderer.toneMapping` alone does nothing for the custom material. Re-rate "Exposure/tonemap" from "easy" to "the architectural decision of Phase 0."

#### M2. Screen-space trail accumulation contradicts the always-moving camera **[verified — medium]**
**Plan claims:** approach §6 makes mouse parallax always-on; §1 catalogs auto-orbit, zoom, follow-cam — alongside screen-space trail accumulation.
**Failure mechanism:** v2's fade quad worked because Canvas2D has no camera. The accumulation buffer is screen-anchored; under camera motion, pixel history no longer maps to world points, so bright content ghost-streaks in the camera-motion direction (follow-cam even inverts trails: the tracked creature loses its trail while the background streaks). Subtle at v2-default trail settings, blatant at high settings or continuous orbit. Discovery timing is the real defect: parallax lands in Phase 2, *after* Phase 0 locks the trail architecture with a static camera — violating the plan's own "risk retires front-to-back" claim. Note: exact reprojection is harder than it looks (no depth buffer exists with depthWrite off), so the realistic mitigation is (a).
**Fix:** Decide the coupling in Phase 0: (a) modulate fade toward 0 proportional to per-frame camera delta (cheap, good enough), (b) approximate 2D reprojection in the decay shader, or (c) freeze camera when trails exceed a threshold.

#### M3. Spine frame construction is unspecified and will roll/flip; no parallel-transport/RMF anywhere in the plan **[verified — medium; merges 2 findings]**
**Plan claims:** approach §5: "compute the tangent numerically, build a local frame (normal + binormal via cross products)" — presented as solved.
**Failure mechanism:** A cross-product frame needs a reference. Frenet is degenerate at every inflection of a two-wave spine; a fixed up-vector rolls as the tangent sweeps (worst-seed closest approach ~20°) and *hard-flips* at sway ≳1.5–2 — a whole ring's dot targets jump ~180°, easing turns each flip into a visible "ring rolls over" glitch, and per-dot normals invert so the lit side flickers. The Phase 0 default-sway eel likely passes; the shipped sway slider (to 2.4) and Phase 1's *vertical* stems (kelp/flower: tangent ∥ world-up at rest — guaranteed degenerate under a naive world-up frame) do not. The register has no frame-stability entry.
**Fix:** Specify rotation-minimizing frames (double-reflection method, ~20 lines) in the Phase 0 plan, seeded deterministically from the creature's seed. Add "no ring flips across the full sway range" to Phase 0 exit criteria; use a non-world-up reference for vertical archetypes in Phase 1.

#### M4. "Normals for free" is false for the sheet archetypes, and the Phase 0→1 gate structure cannot catch it **[verified — medium; merges 2 findings]**
**Plan claims:** breakdown §2.1: "every dot's offset direction from the spine *is* its surface normal — we get normals for free"; Phase 1 exit: squint test + 60fps; Risk 10 covers only the gate *failing*.
**Failure mechanism:** Verified against v2: ray (~90% of dots) and bloom petals (~72%) are (u,v) *sheets* — the offset-from-spine direction lies *in* the surface plane, so Lambert lights the rim and leaves the face flat: exactly wrong, not approximate. Fin planes likewise. (Tube-ish archetypes — eel, octo/star arms, kelp strands, medusa bell — are fine or fixable; amorph can take a deliberate radial pseudo-normal.) The eel is the single best case for the recipe; Phase 0 validates on it, then Phase 1's exit tests silhouette, not shading — so the go/no-go passes while 2–3 archetypes read flat next to lit tubes, and no register item covers normal generalization. The fix is bounded per-archetype math (∂P/∂u × ∂P/∂v for sheets), not a redesign — but it is unestimated work in a phase scoped as one line.
**Fix:** Add one adversarial creature (ray or bloom — *not* amorph) to the Phase 0 spike. Write a per-archetype normal-strategy table before Phase 1 (tubes → ring offset + taper tilt; sheets → analytic surface normal; strands → cylinder normal with radius floor; volumes → radial/depth-rim). Phase 1 exit: every archetype shows directional shading (or a documented deliberate alternative), screenshotted at two light azimuths.

#### M5. At documented parameter ranges, spine curvature exceeds tube radius **at default sway** — rings interpenetrate and Lambert speckles **[verified — medium]**
**Plan claims:** approach §5 spine + sway 0.2–2.4 carried over as "trivial (exists)."
**Failure mechanism:** Verified against v2 numbers (A≈27, w≈2.2, L≈270, R≈17): κ·r ≈ 1.2 at *default* sway (up to ~4.5 for worst seeds), and the two incommensurate waves make near-planar max-curvature alignments sweep along the body continuously. Where the radius of curvature drops below tube radius, opposing ring walls interleave with near-opposite normals → lit/shadow speckle exactly at the visually prominent bend, and the "crisp ribs" scramble. High curvature is also where any frame rotates fastest (compounds M3). Misdiagnosis hazard: "we argue about light, not code" steers debugging into the shader when the defect is spine geometry. (Self-intersection of distant coils was checked and does *not* occur — x is strictly monotone.)
**Fix:** Compute κ(s,t) from the same finite differences and either scale effective sway so max κ·r ≤ ~0.7 or locally shrink ring radius as κ·r→1 (standard tube-extrusion practice). Map the sway slider through this normalization. Screenshot at sway 2.4 in Phase 0, not just default.

#### M6. CPU budget "~24k × ~10 trig = 1–2 ms" fails its own arithmetic, and its cited evidence is misquoted **[verified — medium]**
**Plan claims:** approach §2/§7; "measured headroom in v2 was already fine."
**Failure mechanism:** 240k `Math.sin/cos` at realistic V8 throughput (10–25ns) is ~2.5–6 ms of trig alone — the budget's own op count contradicts its own ms figure, and Alternative A's rejection leans on it. The "measured headroom" is actually CLAUDE.md's *total* frame measurement (54–60fps with 12 creatures — already missing 60), dominated by Canvas2D drawing; no isolated math-loop measurement exists. v2's heterogeneous dot objects also make the shared update loop megamorphic. Risk 4 names the CPU ceiling but rates it Medium on the flawed premise; its governor mitigation would fire on target hardware, sacrificing the density that motivated the rebuild.
**Fix:** The structure §5 already gestures at, made mandatory: compute the frame once per *station* (~52), place dots with precomputed static ring angles — ~1 trig/dot amortized. Static per-dot params in flat typed arrays (needed for BufferGeometry uploads anyway). Measure the isolated loop in Phase 0 under 4× CPU throttle.

#### M7. The gate bar ("beats v2") is a much lower bar than the goal ("fidelity of the reference video"), with no comparison procedure **[verified — medium]**
**Plan claims:** approach goal line; Phase 0 exit "you look at the eel and say it clearly beats v2"; CLAUDE.md decision 4 "expectation set."
**Failure mechanism:** The Risk 7 agreement is one sentence resolving a different gap (not-photoreal), not a visual target. Any tonemapped additive-glow render clears "beats v2" (flat squares) almost automatically — approach §1 itself argues glow alone transforms the look — while the user's real anchor is the yuruyurau video. The comparison procedure is undefined (one spotlit eel vs. what?), and if the verdict is "better than v2 but still not it," the plan's only script is "argue about light" — no re-scope path, since §3 already rejected all alternatives. Cost if it fires: a repeat of the v2 disappointment beat after Phases 1–2, though mostly tuning rework, not a rewrite.
**Fix:** Before Phase 0: 2–3 annotated stills from the reference ("this we match / this we don't"). Gate comparison: Phase 0 screenshot beside a v2 eel *and* a reference frame; pass = "closer to the reference than to v2." Pre-agree the failure branch.

#### M8. Risk 2's "must be in Phase 0" cannot be validated in Phase 0 — one eel can't reproduce the blowout condition **[verified — medium]**
**Plan claims:** Risk 2: dense overlaps from "schools, big creatures"; mitigation includes "auto-reduce alpha as creature dot-count rises"; §5: blowout "settled in Phase 0."
**Failure mechanism:** Only the plumbing is settled in Phase 0; the density-adaptive behavior is untestable in a one-eel scene, and the per-creature dot-count alpha scaling never fires for *cross-creature* overlap — a "school of fish" is multiple creatures. First real exercise of the failing condition is Phase 1; the cited regression check is Phase 3. (Attenuated: a coiling eel + trails does exercise substantial pileup, and Phase 1's screenshot sweep would catch a blown-out school; the fix is a local tuning pass, not rework.)
**Fix:** Add a synthetic worst case to Phase 0 headless screenshots: the hardcoded eel duplicated 6–10× overlapping (no lexicon needed). Name "school blowout screenshot" as the Risk 2 checkpoint in the *Phase 1* exit criteria.

#### M9. No three.js version is pinned, and r152+ color management sits directly under the project's #1 visual risk **[verified — medium; merges 3 findings]**
**Plan claims:** CLAUDE.md "prefer a modern three version" (no version named anywhere); Risks 1–3 and the §4 shader were all analyzed against r128 semantics; the re-check instruction covers Risks 1 and 3 but *omits Risk 2 — the most affected*.
**Failure mechanism:** Since r152: ColorManagement on by default, sRGB output, `THREE.Color` uniforms linearized (so `uColor` — the color control — renders different tints than r128), tonemap+sRGB relocated into OutputPass, addons at `three/addons/`. The custom ShaderMaterial gets *no* colorspace/tonemapping chunks injected, so every hand-tuned constant in §4 (core/halo/fog) was tuned for a pipeline that no longer exists; double-encoding sRGB (hand-rolled final quad + OutputPass) washes everything pale gray — a classic migration bug; and ACES desaturates/hue-shifts deep blues toward purple, i.e., maximum exposure for a blue/cyan-identity product with a color control. Breakdown Phase 3 still plans "hand-rolled bloom" (an r128 assumption) while CLAUDE.md prefers the official composer. The Phase 0 gate will encode one unrecorded version's pipeline; an uncommitted lockfile or casual bump silently re-grades the gated look later.
**Fix:** Pin an exact three version (no caret), commit the lockfile, and record in CLAUDE.md next to Risks 2/3: ColorManagement on; exactly one sRGB encode and one tonemap (OutputPass owns both); §4 constants to be deliberately re-tuned in Phase 0, not trusted. Any three upgrade re-runs the Phase 0 visual gate. If ACES desaturation kills the color control, evaluate AgX/Reinhard-luminance before locking the look.

### MEDIUM — unverified

- **M10. Stale bounding sphere frustum-culls swimming creatures out of existence.** `geometry.boundingSphere` computes once from the spawn noise-cloud and never updates from attribute writes; with world coords baked into positions (the v2 port pattern), creatures vanish mid-screen as the stale sphere exits the frustum — a classic three.js particles heisenbug ("eel disappears when I move the mouse"). Better fix than the reflex `frustumCulled=false`: keep dots in creature-local space, drive placement/heading via the object matrix (also deletes 24k CPU rotation ops/frame), set a fixed local sphere from `arch.rad`, and skip target math for fully offscreen creatures. *(merges 2 findings)*
- **M11. DOF must conserve energy.** "Larger and fainter" with alpha ∝ 1/k makes total contribution grow by k: racking aperture makes defocused creatures *brighter* (opposite of a lens) and pushes accumulation into ACES clipping and across the bloom threshold; fill also scales k² so the aperture slider is an overdraw slider Risk 5 never budgeted. Fix: alpha ∝ 1/k² (still two lines — the correct two), cap k, include aperture-at-max in Phase 0 measurement.
- **M12. Uniform-x stations aren't uniform in arc length.** Rib spacing varies ~1→2.2× (to ~4.8× at high sway) between crests and crossings, and the bunching pattern *travels* — ribs visibly breathe and total body length pulses with wave phase (an eel is inextensible). Fix: sample ~200 points, prefix-sum, place 52 rings at equal arc-length fractions; size by arc length, not x-extent.
- **M13. The approach doc's buffer/shader architecture predates the lighting plan.** §3 has no normal attribute, §4 no light uniforms and *linear* fog (vs CLAUDE.md's "exponential") and bakes fog pre-tonemap. Normals are a second dynamic attribute (doubles upload; per-dot frame rotation absent from the budget), and eased positions desync from target-computed normals — dots mid-formation get lit as if already on the ring surface, wrong exactly at the PRD's "magic beat." Fix: amend §3–4 before Phase 0 (interleave position+normal; ease normals with the same coefficient and renormalize in-shader, or fade the directional term in with formation progress); re-run the §7 upload arithmetic. *(merges 2 findings)*
- **M14. Determinism has three unpinned break points.** (a) v2 already couples geometry to spawn context (`dotScale` mutates `arch.n` and `P.scale`), and a build-time density governor makes the same URL render different creatures on different machines; (b) the 3D port must draw new params from the same mulberry32 stream — any inserted draw reshuffles everything downstream, and no doc freezes call order; (c) wall-clock never-repeating pose vs screenshot-based gates (see H3 corollary). Fix: density as render-fraction only (drawRange/discard, never build-count); document rn() draw order as a frozen interface; injectable fixed-step clock.
- **M15. Risk 4's governor has one lever and no diagnosis — and it's the wrong lever for post-chain cost.** Full-screen passes are dot-count-independent: a post-bound iGPU makes the governor ratchet density to the floor while jank persists. And drawRange truncation on v2's ring-ordered build cuts the creature's *back half* off instead of thinning it — a Phase 1 data-layout decision made implicitly, discovered as Phase 4 rework. Fix: lever ordering (renderScale/DPR → sprite cap → dot fraction); deterministic cross-ring shuffle at build time so any prefix is a uniform subsample.
- **M16. First-spawn shader compile lands on the formation beat.** Per-creature `#define` variants (invited by two-tone/iridescence options) each trigger synchronous compile+link (10–100ms+ on iGPU drivers) plus GPU buffer allocation on the Enter keypress. Fix: one program, uniform-driven variation; `renderer.compile()` prewarm; pooled max-size geometry per archetype.
- **M17. npm/vite has no delivery story and breaks two conventions nobody updated.** ES modules fail on `file://` (CORS) — Risk 9's own "zip" mitigation doesn't run when double-clicked; the shareable-URL feature has no hosting story; "single testable HTML file" was a load-bearing argument in §3's A-lite comparison; the "load page" test convention now means dev server (HMR websocket noise trips the console-error gate; different perf) or an unbuilt dist. Fix, written into CLAUDE.md as Phase 0 task #1: dev = vite; ship = `vite build` + `vite-plugin-singlefile` (or a named static host); tests run against built output via `vite preview`; strike Risk 1, add a build/delivery risk. *(merges 3 findings)*
- **M18. `threejs-approach.md` is stale but still labeled "the architecture for v3."** It specifies in detail the fade quad (§3) that CLAUDE.md and Risk 3 forbid, plus r128/cdnjs (§8) and hand-rolled-bloom reasoning the npm decision obsoletes. A fresh implementer reading the normative doc top-to-bottom builds the forbidden plumbing — Risk 3's "deciding late = rework" caused by an un-updated doc. Three docs currently give three different trails answers. Fix: edit §3/§8 or add a SUPERSEDED header naming the conflicting sections.
- **M19. PRD success criteria are unmeasurable or already invalidated, with no replacement.** "≥7 of 10 common animal names" is structurally unachievable under ocean-only scope ("cat" hashes to a random sea creature); "median session > 3 min" requires analytics the PRD's own non-goals prohibit; "living thing in under a second" contradicts the PRD's own 1.5s formation beat. - **M20. - **M21. - **M22. Stills cannot gate a motion-defined aesthetic.** The rebuild's selling points are temporal (non-repeating coil, the 1.5s formation, twinkle, idle rotation); three stills can be perfect while the loop visibly repeats or formation is janky, and periodic screenshot intervals can alias with twinkle phase.
